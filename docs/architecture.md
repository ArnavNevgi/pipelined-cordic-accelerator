# Architecture

## Design Objective

The design implements a pipelined sine/cosine accelerator using rotation-mode CORDIC. It is intended to demonstrate a complete FPGA-oriented RTL flow: fixed-point algorithm implementation, streaming flow control, simulation-based verification, numerical comparison against a golden model, and FPGA implementation reporting.

The current RTL supports signed Q2.14 input angles in the range `-pi/2` to `+pi/2` radians and produces signed Q2.14 sine and cosine outputs.

## CORDIC Algorithm

CORDIC computes trigonometric functions through a sequence of shift-add micro-rotations. The RTL tracks three signed state values:

- `x`: cosine component
- `y`: sine component
- `z`: residual angle

For stage `i`, the rotation decision is based on the sign of `z`:

```text
if z >= 0:
  x_next = x - (y >>> i)
  y_next = y + (x >>> i)
  z_next = z - atan(2^-i)
else:
  x_next = x + (y >>> i)
  y_next = y - (x >>> i)
  z_next = z + atan(2^-i)
```

The RTL uses arithmetic right shifts (`>>>`) so signed Q2.14 values preserve sign during each shift.

## Pipeline Organization

The core contains 16 CORDIC iteration stages. Each stage registers `x`, `y`, `z`, and a valid bit. A new input transaction initializes stage 0:

```text
x_0 = CORDIC_K
y_0 = 0
z_0 = angle_in
```

The registered pipeline structure is:

```text
input handshake -> stage 0 -> stage 1 -> ... -> stage 16 -> output handshake
```

This organization provides fixed-latency behavior when the downstream interface is ready and one output per cycle after the pipeline is filled.

## Valid-Ready Flow Control

The core uses a valid-ready streaming interface:

- `in_valid` and `in_ready` qualify input acceptance.
- `out_valid` and `out_ready` qualify output acceptance.

The design uses a global-stall backpressure scheme:

```text
pipe_advance = out_ready || !valid_pipe[STAGES]
in_ready     = pipe_advance
```

When the output stage is valid and `out_ready` is low, the pipeline does not advance. All registered `x`, `y`, `z`, and valid bits hold their previous values. This prevents output loss and preserves every in-flight transaction.

## Gain Compensation

Rotation-mode CORDIC introduces a deterministic gain. The RTL compensates for this by initializing `x` with the reciprocal gain:

```text
CORDIC_K = round(0.607252935103 * 16384) = 9949
```

This value is defined in `rtl/cordic_pkg.sv` and documented in `reports/golden_generation_summary.txt`.

## Arctangent Lookup Table

Each stage uses one arctangent constant:

```text
ATAN_TABLE[i] = round(atan(2^-i) * 2^14)
```

The lookup table has 16 entries and is stored in `rtl/cordic_pkg.sv`. The table is generated by `scripts/gen_golden.py` and recorded in `reports/atan_table_q214.txt`, keeping the RTL constants traceable to the Python reference model.

## Output Mapping

After all CORDIC rotations, the final registered `x` and `y` values are mapped directly to cosine and sine:

```text
cos_out = x_pipe[STAGES]
sin_out = y_pipe[STAGES]
```

Both outputs are signed Q2.14 values.

## Latency and Throughput

The datapath contains 16 CORDIC iteration stages. The current benchmark reports a first-output handshake latency of 17 cycles because the testbench measures from accepted input transaction to accepted output transaction.

Under continuous downstream readiness, the output-span throughput is:

```text
1.000000 outputs/cycle
```

With randomized input valid gaps and randomized output backpressure, the measured output-span throughput is:

```text
0.713479 outputs/cycle
```

The lower randomized result is expected because global backpressure stalls the full pipeline whenever the downstream sink is not ready.

## Design Tradeoffs

The design uses a global-stall pipeline rather than per-stage elastic buffering. This keeps the control logic simple and easy to verify while still preserving all transactions under output backpressure.

The CORDIC datapath uses shifts, additions, and subtractions instead of multipliers. Vivado post-route utilization reports show zero DSP and zero BRAM usage, which is consistent with the shift-add implementation.

The current angle range is limited to `-pi/2` to `+pi/2`. Wider angle support would require quadrant correction or argument reduction around the existing core.
